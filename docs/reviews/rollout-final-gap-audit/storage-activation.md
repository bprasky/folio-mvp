# Protected project photos: activation and legacy transition

This is a prepared operating procedure, **not an executed production migration**. No bucket policy, production object or user record was inspected or changed in this task. There is no Prisma migration in this PR.

## New objects

1. In an authorized disposable Supabase project, provision a **separate private** bucket named `project-photos`, or set `FOLIO_PRIVATE_PHOTOS_BUCKET` to another private bucket. Keep `event-images` and `product-meshes` unchanged. Set the object limit to 20 MiB and accepted image types to JPEG/PNG. Do not grant anonymous/authenticated direct object select, insert, update or delete policies for this bucket. The server service role performs writes and reads; never expose its key to a client.
2. Deploy the code only after the bucket and server credentials are available. `saveBufferToProjectStorage` checks the bucket's `public === false` before writing and fails closed if it is missing/public. A missing bucket therefore blocks photo intake; it is a release prerequisite.
3. Browser content stores canonical `/api/project-photos/<project>/<path>` URLs. The dynamic route checks current project access or included/public eligibility on every request. Owners, allowed participants and active firm roles can see drafts. Anonymous users can see only currently published included photos and eligible source-bound crops.
4. Responses send private/no-store browser, CDN and Vercel cache headers. The image loader sends these URLs directly; middleware refuses both relative and absolute protected URLs at `/_next/image`. The connected Next acceptance test verifies this denial and real image rendering. Recheck these headers and any custom/CDN proxy behavior on the hosted deployment.
5. Server processing reads bytes with an authorized project ID, or issues a **60-second** signed URL for a remote image provider. Signed URLs are bearer credentials and remain usable until expiry even if a project is unpublished in the interim. They are not stored in article/export data. Already-downloaded bytes cannot be revoked. Browser URLs themselves are reauthorized immediately after exclusion/unpublishing/deletion.
6. Crops are immutable private objects. Tag moves/repositioning clear the old crop. Crop attachment compares the source tag's image, position and update timestamp, and commits metadata together. Stale output stays unreferenced and is inaccessible through the proxy; it may need later private-orphan cleanup.

## Legacy inventory and copy-before-switch

**Changing a database URL does not revoke an old public URL.** The isolated migration test deliberately proves that old bytes remain accessible after copying, and that a shared import must not be deleted. Hosted legacy retirement is a rollout blocker.

Run the following only against an explicitly approved inventory, beginning with disposable synthetic projects:

1. Export a manifest with project/image/tag IDs, old URLs, object bucket/path, intended visibility, exact current references and a SHA-256 of each object. Inventory all `ProjectImage.url`, `ProductTag.cropUrl`, linked `Selection.photo`, post/Instagram-export image references, and legacy generated derivatives. Search string-valued references in relevant JSON content as well as structured columns. Keep the manifest and backup private; do not place user URLs/content in this repository.
2. Classify each source: owned project object; shared/imported object; external/catalog image; or unresolved. Validate the exact configured storage origin and bucket/path ownership. A matching hostname or a project-looking string is insufficient proof of ownership. Do not import arbitrary manifest URLs without the existing bounded SSRF-safe transport, or use direct service-role bucket download for verified owned objects.
3. Copy each verified owned photo/crop into the new private bucket, using a fresh immutable path under its authorized project. Decode/sanitize using the existing Sharp processor; record old/new URL, hash, size, dimensions and any orientation/format transformation. Do not delete or overwrite the source. The protected destination must exist before switching references.
4. In a short transaction, lock the project row and compare the exact old values before updating each image/crop/linked selection and each reviewed persisted image reference. Update only that project's references. A mismatch means stop/re-inventory; do not overwrite newer edits. Invalidate affected project/public profile/article caches after commit. Preserve factual text, attribution, image IDs, order, rooms and inclusion. Public projection resolves image IDs to current URLs, but this does not excuse auditing legacy JSON consumers.
5. For shared/imported media, enumerate **all** referencing projects/products/content before any retirement. Each legitimate recipient may need an independent authorized copy. Keep intentionally public external/catalog images public and leave external owners' objects alone. Unresolved provenance stays flagged; do not silently certify it as protected. Never delete a source merely because one project's row was switched.
6. Verify owner/collaborator/anonymous bytes, image dimensions, published pages, native export and protected processing in the disposable project. Repeat after exclusion, unpublish, revocation and deletion. Test the original public URL separately. For a source that should become private, retire its old public object only after all approved references have moved and caches are handled. If legitimate public sharing requires its continued existence, record that its bytes remain public; it cannot meet a confidentiality claim.
7. Verify remaining direct public URLs and backup/export copies. Public-cache retention and third-party copies may prevent immediate or complete historical revocation. Obtain the deployment operator's explicit acceptance of the actual exposure/retirement plan before inviting private uploads.

## Rollback and cleanup

- Keep new private objects and the service route available when rolling back unrelated application changes. Rolling back to code that cannot read protected URLs can break published content.
- The old/new manifest permits a compare-and-set reference rollback while original objects remain. The isolation test verifies that technical reversibility; **do not automatically restore public URLs for content that should be private**. A privacy rollback should retain the private route or temporarily stop intake/publication while fixing it.
- Do not flip a legacy shared bucket public/private as a shortcut. Do not delete successful deterministic objects in failed-request cleanup. The concurrency test forces one DB write to fail while another request successfully uses the same immutable object.
- Garbage collection is separate: confirm no live image/tag/export references, include a grace period covering in-flight requests, then delete only reviewed private orphan paths. No new production garbage-collector job is added by this PR.

## Verification performed and still needed

`scripts/rollout/privacy-storage.test.cjs` uses actual HTTP files, actual Supabase client requests, Sharp decoding and native PostgreSQL. Its policy service is a local fixture, not Supabase RLS. It tests byte denial, metadata stripping, owner/viewer access, source-bound crop visibility, expired provider URLs, immutable concurrent uploads, forced-DB-failure cleanup and the copy/shared-reference/rollback procedure. `connected-journey.cjs` additionally runs the real Next router, session and optimizer plus native carousel JPEG export.

Hosted Supabase policy/byte/cache verification, inventory/backfill/retirement of existing URLs and physical browser/provider checks remain open. Optional SAM/3D paths still use the legacy catalog/mesh infrastructure and have not been activated or certified here. Do not promise private-photo-derived 3D outputs until their source/derivative storage and provider flows receive a separate authorized verification. Catalog cutouts use product images and remain separate from project-photo intake.

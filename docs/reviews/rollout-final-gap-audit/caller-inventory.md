## Request compatibility

Project and room identities are scoped on the server to the authenticated actor and firm/project. Unique deterministic UUIDs arbitrate independent database connections. A fresh operation can intentionally use the same title/name and gets a separate row. Reusing an operation identity with different normalized values, or after that saved object has been edited, returns 409 with a recovery message. This conservative policy does not overwrite the saved object or create a second one.

Old cached clients that omit project/room identity or tag prior state must reload. Every supported source caller was updated together; no silent unguarded legacy overwrite remains on the changed routes. A server acknowledgment clears a room's pending identity so the next deliberate same-name creation remains possible. An uncertain result retains it across remount/reload. Manual project snapshots are tab-scoped session storage; when browser storage is disabled, the mounted form retains retry identity but refresh recovery is unavailable. Clearing browser storage necessarily discards unsent client recovery.

The project writer removes the pending snapshot only after a confirmed create. Subsequent edits go to that saved ID. If another session has edited the saved object before the original create retry resolves, open that saved project as instructed rather than manufacturing a fresh identity and duplicate. Authentication and permission failures keep entered fields and do not trigger automatic writes.

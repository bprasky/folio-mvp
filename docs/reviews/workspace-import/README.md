# Signup and background website import

New professional signups now move through personal account → business access → workspace preparation. Browsing remains available without a business; posting permissions are unchanged. The same preparation step is reachable from the diagnostic and firm onboarding routes, and existing members can return from their professional account.

The owner enters one website and selects business details, their own bio, and/or projects, then explicitly consents to website reading, private copying and a readiness email. The crawler discovers the pages; onboarding no longer asks for individual bio or project links. Business profile changes require a separate review/save. Bio text becomes interview context, without replacing published copy or accepted answers. Projects are canonical private drafts with no inferred completion date or room assignments. Website import does not generate interview questions. The next step is a finish schedule or manual tagging; questions are generated from current context when the person enters the interview. Legacy website-import opening plans are ignored for new sessions, without changing existing answers or active sessions.

## Operation

- Existing `ImportSession.processingMeta` stores namespaced `workspace-import-v1` runs. No schema change, new service or dependency is required.
- `/api/cron/workspace-imports` is triggered every minute by the Vercel cron entry. `CRON_SECRET` authenticates it. The worker uses full-JSON compare-and-swap, a six-minute lease and a checkpoint after every page/photo. Function duration is bounded to 300 seconds; the worker stops starting new units well before that limit.
- Actor and business permissions are checked at start, before each unit and before committing project assets. Profile application uses version checks and a transaction. Legacy import mutation endpoints reject these runs.
- Starts are serialized per actor using a transaction advisory lock: one active run and five new runs per day. Each run reads at most 18 pages, 10 projects and 30 photographs per project; manual retries are capped at three. Source/request identities prevent repeated starts and retries from duplicating projects or photographs.
- Public web fetches reuse DNS-pinned safe transport. Optional `RENDER_WORKER_URL` / `RENDER_WORKER_API_KEY` support pages needing rendering; static content remains useful if rendering fails. Images use the existing validated private project storage. Logos are decoded/re-encoded as bounded PNG review candidates.
- `RESEND_API_KEY` and `CRON_SECRET` must be configured before the import offer is enabled. Existing private project storage credentials are required for photographs. Existing model configuration prepares questions on interview entry; deterministic project questions remain available if generation falls back. No browser process owns the run.
- Readiness mail uses a persisted immutable payload and an idempotency key. Retry delays are recorded; ambiguous submission is never retried outside the provider's deduplication window. Manual recovery does not resend an already accepted email. Accepted is not a delivery receipt. Hard permission loss/repeated worker interruptions pause the run and expose recovery in the workspace.

## Prepared profile handoff

The later approved completion experience shows a private profile preview, with imported identity/About/bio, project photography, and muted “Private draft” cards. It is an authenticated onboarding view, not a new public profile design or automatic publication. Its project titles, photographs and public/private state come from current records scoped to the importing person and business. Existing saved profile edits remain visible on return. The cover prefers larger landscape photographs using saved dimensions, with source-order fallback for earlier imports; this is deterministic composition, not an AI quality claim.

The next step selects the run's business context before entering `/project/:id?view=media&step=tags&action=import-doc` for a finish schedule or `action=tag-by-hand` for manual tagging. Projects without photos offer photo entry first; read-only members are not offered material-editing actions. Schedule uploads stage candidates; reviewing and placing products on photos creates the same sourcebook records as manual tags. The existing deliberate Continue to interview action then prepares questions. No new publication or all-photo tagging requirement is introduced. Editable profile details and import diagnostics remain available below the preview.

The content-ready checkpoint and an idempotent `WORKSPACE_IMPORT_READY` notification commit in one transaction. A gentle in-app notice checks the signed-in person's existing notifications while Folio is visible and links to the same preview used by the email. Acknowledging it preserves the normal notification history. Retries do not duplicate or reset it. Completed content can be reviewed while delivery retries wait, once the worker lease is released; email messages still use the existing immutable payload and provider idempotency rules. There is no schema change for this handoff.

Additional validation: the workspace suite checks cover selection, missing-photo/read-only/published UI states, current project edits, matching email/in-app destinations, deduplication and preserved read state, delayed-email review access, and no premature or unauthorized notice. The same PGlite-versus-boundary-double limits above apply. Targeted lint, client boundaries, the TypeScript ratchet (864 existing diagnostics versus 880 baseline, no new fingerprints), and production compile passed. Browser walkthroughs covered the one-URL consented start, automatic progress-to-preview transition, profile review disclosure, correct schedule/manual tagging destinations, notification-to-preview return, a 390px phone viewport without horizontal overflow, and readable actions/draft labels with the current dark-mode setting. Fixture accounts/results are synthetic; existing stock photography stands in for project assets.


Reviewed photo tags contribute only normalized material themes to interview context, alongside image analysis. They do not populate vendor insights or product question subjects. Both standard question generators instruct the model to cross-check these clues against the current photos, keep uncertainty tentative, and focus on design choices rather than specific products or testimonials. Standard room generation no longer resolves subscription eligibility or passes product names; it rejects responses that declare product/vendor subjects or commercial question types. Existing dedicated spotlight/boost systems are outside this change.

Additional regression evidence: no question calls occur during import; accepted manual/schedule tags and confirmed finishes reach material context, while product identities remain in the sourcebook; unreviewed scraped products are excluded; repeat pins do not multiply material themes; opening questions are generated only on interview entry. Prompt tests capture the actual model request and reject commercial room outputs. These synthetic provider tests verify the contract, not live-model editorial quality.
